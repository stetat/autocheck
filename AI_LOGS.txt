⏺ 1. No functional problem — I conflated two things.

  Sorting by price is correct and stays exactly as is. The API sorts faithfully;
  nothing is broken. The only issue is that the generated numbers aren't
  brand-correlated, so a Cobalt at 16.9M ₸ outranks a Mercedes. That's cosmetic
  realism of fake data, zero impact on the service. Per-model tiers would only
  change what the generator writes, never how sorting works. Given it's purely a
  credibility detail in a demo table, I'd leave it unless you want it.

  2. Why a directory sweep — and what it actually risks.

  The scheduled trigger needs a source, and a partner dropping files into a
  folder (SFTP/shared mount) is how 1C integrations usually run. But my
  implementation ingests every CSV every tick, which opens four real failure
  modes:

  - Filename ordering breaks past 9 files. Proven above: sorted() gives day1, 
    day10, day11, day2, day3. Since later feeds overwrite earlier ones by
    design, day2's stale mileage would land after day11's — silently writing old
    data over new. This is the serious one.
  - Every tick reprocesses all history. You saw it live: updated: 235 on a sweep
    that changed nothing. At 60s intervals the run log fills with no-op runs,
    and cost grows with directory size rather than with new data.
  - Partial-file race. A partner still writing feed.csv when the sweep fires
    gets parsed half-written — rows rejected, or worse, a truncated-but-valid
    file ingested as if complete.
  - Stale files resurrect data. An old feed is re-applied forever, so a car
    pulled from a newer export keeps being revived by the older one.

  What I'd recommend (small, and it kills the first, second and fourth): order
  by file mtime instead of filename, and skip files whose (name, mtime, size)
  matches an already-processed run — so a tick with no new drops does nothing
  and logs nothing. The partial-write race needs either an atomic-rename
  convention (.tmp → .csv) or ignoring files modified in the last few seconds;
  the rename convention is standard and I'd document it in the README rather
  than code around it.

  That's roughly 30–40 minutes with tests. Alternatives: ingest only the newest
  file per tick (simpler, but a missed tick loses a feed), or drop the sweep and
  make the scheduler re-read one fixed path (simplest, least realistic).

  Want me to do the mtime + skip-unchanged fix before Phase 4, or note it as
  known and move to the frontend?
