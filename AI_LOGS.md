## 2. Фаза 1 — генератор датасета 1С

**Задача (поставлена в рамках того же промпта «start implementing the plan»):**
сгенерировать реалистичную выгрузку 1С, пригодную для демонстрации upsert.

**Что сделал ИИ:** `scripts/generate_feed.py`, воспроизводящий особенности реальной
выгрузки 1С: кодировка windows-1251, разделитель `;`, кириллические заголовки,
запятая как десятичный разделитель, даты `DD.MM.YYYY`, неразрывный пробел в разрядах,
свободный текст в поле «Дефекты», валидная контрольная цифра VIN (ISO 3779),
~6% «грязных» строк (пустой VIN, обрезанный VIN, `н/д` в пробеге, пустая цена).

Сгенерированы два файла: `feed_day1.csv` (120 строк) и `feed_day2.csv` (130 строк),
где 83 VIN повторяются — это и есть материал для проверки upsert.

**Проблемы и правки (обе найдены при проверке вывода, а не «на глаз»):**
1. **Пробег уменьшался.** У перенесённых во второй файл машин поля генерировались
   заново, из-за чего автомобиль «откатывал» пробег: 380 739 → 268 946 км. Введена
   функция `age_row()`: строка второго дня выводится из строки первого дня — пробег
   только растёт, цена дрейфует вниз, иногда добавляется новый дефект. Проверка:
   число регрессий пробега по 83 общим VIN = 0.
2. **Несогласованные характеристики.** Тип кузова, КПП и объём двигателя выбирались
   случайно и независимо от модели — получалась «Lada Niva Travel, седан, вариатор».
   Модели переписаны в таблицу `модель → (кузов, допустимые объёмы)`, КПП выбирается
   из правдоподобного для марки набора.

**Проверено:** контрольная цифра VIN валидна у 100% чистых строк; 83 пересечения
и 47 новых VIN между файлами; 0 регрессий пробега; дубликатов VIN внутри файла нет.

## 3. Фаза 2 — ядро загрузки: парсер + upsert (TDD)

**Задача:** реализовать бонусное требование ТЗ — upsert по VIN без дублей и
юнит-тесты на него. Работа велась строго test-first.

**Как ставилась задача ИИ:** сначала пишутся падающие тесты, фиксирующие
желаемое поведение и API, затем минимальная реализация. Порядок важен: тест,
написанный после кода, проходит сразу и ничего не доказывает.

**Что сделал ИИ:**
- `tests/conftest.py` — конструктор фида (cp1251, `;`, кириллица) и фикстура
  in-memory SQLite. Без моков: гарантия «без дублей» обеспечивается ограничением
  UNIQUE в БД, поэтому мок сессии не проверял бы ничего.
- `tests/test_parser.py` (10 тестов), `tests/test_upsert.py` (7),
  `tests/test_feed_robustness.py` (12).
- `app/parsers/csv_1c.py` — чистый парсер: bytes → `ParseResult(records, errors)`.
- `app/services/ingest.py` — единственный путь загрузки: `ingest_bytes` /
  `ingest_file` / `ingest_directory`. Upsert через `INSERT ... ON CONFLICT(vin)
  DO UPDATE`, `first_seen_at` намеренно исключён из обновляемых полей.

**RED → GREEN подтверждён:** первый прогон падал с `ModuleNotFoundError`
(реализации ещё не было), после реализации — 29 passed.

**Проверка качества самих тестов (мутационный анализ).** Импорт-ошибка — слабый
RED, поэтому в код намеренно вносились дефекты, чтобы убедиться, что тесты их ловят:
1. `ON CONFLICT` заменён на обычный `INSERT` → упало 4 теста, включая головной
   `test_ingesting_the_same_vin_twice_creates_one_row`.
2. `first_seen_at` добавлен в список обновляемых полей → упал
   `test_first_seen_is_preserved_while_last_seen_advances`.
Обе мутации откачены, 29 тестов зелёные.

**Проблемы и разбор:**
- **Дубли внутри одного файла.** SQLite не умеет разрешать конфликт против
  строки, вставленной тем же запросом, — падает с ошибкой. Добавлена функция
  `deduplicate()` (побеждает последнее вхождение VIN) до обращения к БД.
- **Расхождение ожидаемых и фактических чисел.** На реальных фидах ожидалось
  83 обновления, получено 78. Разбор показал, что это ошибка *прогноза*, а не кода:
  оценка «83» считала только длину VIN, а 5 строк имеют корректный VIN, но пустую
  цену или год `19999` и справедливо отбраковываются. Истинное ожидание —
  78 обновлений и 45 вставок, ровно столько и получилось.

**Проверено на реальных данных:** день1 → 112 создано / 8 отклонено; день2 →
45 создано / 78 обновлено / 7 отклонено; в БД 157 машин при 157 уникальных VIN
(дублей нет); повторная загрузка того же файла даёт 0 созданий и не меняет
количество строк (идемпотентность). Покрытие: `services/ingest.py` — 100%,
`parsers/csv_1c.py` — 87%.

## 4. Фаза 3 — два триггера загрузки и API

**Задача:** реализовать оба триггера из ТЗ (по расписанию и принудительно),
не дублируя логику разбора, плюс эндпоинты для фронтенда. Снова test-first.

**Что сделал ИИ:** `app/api/routes.py` (`POST /api/ingest`, `GET /api/vehicles`
с поиском/фильтром/сортировкой/пагинацией, `GET /api/brands`, `GET /api/runs`,
`GET /api/stats`), `app/scheduler.py` (APScheduler, интервальная задача),
`app/schemas.py`. Оба триггера — тонкие обёртки над `services/ingest.py`.

**Три реальных бага, найденных проверкой (все — классические для агентного кода):**

1. **Планировщик был зарегистрирован, но стоял на паузе.** В `add_job` был передан
   `next_run_time=None`; в APScheduler это означает «поставить на паузу», а не
   «запустить по умолчанию». Смоук-тест такое не ловит: задача есть в списке,
   но не выполняется никогда. Написан тест, проверяющий `job.next_run_time is not
   None`, — он упал, параметр удалён.

2. **`DetachedInstanceError` в планировщике.** Поля объектов `IngestRun` читались
   после закрытия сессии. Важно: первая версия теста это *не воспроизвела*, потому
   что в каталоге лежал один файл. Баг проявляется только с двумя и более файлами —
   коммит второго прогона обесценивает (expire) объект первого. Тест переписан на
   два файла и упал как надо.

3. **`HTTP 500` на вебхуке с несколькими файлами.** Та же первопричина в другом
   месте: `IngestRunOut.from_run` сериализовал устаревший объект, `model_dump()`
   возвращал пустой словарь, Pydantic падал на «missing fields». Найдено только
   при живой проверке curl'ом — юнит-тесты с одним файлом проходили.

**Разбор первопричины.** Вместо латания двух мест исправлена причина:
сессии создаются с `expire_on_commit=False` (в `db.py`, `scheduler.py` и в
тестовой фикстуре — чтобы тесты повторяли продовое поведение). Отдельный урок:
широкий `except Exception` в задаче планировщика превращал настоящий баг в
безобидную строчку лога, поэтому добавлен тест, требующий чистого лога без ERROR.

**Проверено:** 51 тест зелёный; на живом сервере планировщик сработал сам
(2 прогона на старте → 6 через 12 секунд, 0 строк ERROR); `POST /api/ingest`
возвращает 200 и для каталога, и для загруженного файла; не-CSV → 400;
`sort=;DROP TABLE vehicles` → 422 (сортировка ограничена белым списком);
в логе 0 ошибок 500.

## 5. Обход каталога: порядок по mtime и пропуск обработанных файлов

**Промпт:**
> yes, make order by file mtime, and dont process already processed files.

**Контекст.** При разборе фазы 3 человек спросил, зачем обход каталога и какие
ошибки он допускает. Разбор выявил четыре проблемы, из них одна серьёзная:
файлы обходились в **лексикографическом порядке имён**, а `feed_day10.csv`
сортируется раньше `feed_day2.csv`. Поскольку более поздняя выгрузка по замыслу
перезаписывает раннюю, начиная с десятого файла устаревшие данные молча
записывались поверх свежих. Плюс каждый тик переобрабатывал всю историю
(в живой проверке — `updated: 235` при нулевых изменениях).

**Что сделал ИИ:**
- Сортировка кандидатов по `st_mtime`, а не по имени.
- В `IngestRun` добавлены `source_mtime` и `source_size`; обход пропускает файлы,
  для которых уже есть **успешный** прогон с той же тройкой (имя, mtime, размер).
  Учитываются только успешные прогоны — иначе разовый сбой навсегда занёс бы файл
  в чёрный список.
- `skip_unchanged=False` и параметр `POST /api/ingest?force=true` — чтобы
  принудительная загрузка при необходимости всё же переобработала всё.
- Размер учитывается вместе с mtime: перезапись файла в ту же секунду иначе
  осталась бы незамеченной.

**Изменение поведения зафиксировано осознанно.** Два существующих теста
(`test_webhook_is_idempotent_across_calls`, `test_runs_endpoint_returns_history_newest_first`)
закрепляли прежнюю семантику и были переписаны намеренно — под новое требование,
а не «чтобы прошли».

**Проверено на живом сервере:** после старта 1 прогон / 112 машин; после 12 секунд
простоя (4 тика интервала) — по-прежнему 1 прогон и 112 машин, то есть повторной
обработки нет; после того как в каталог положили `feed_day2.csv` — 2 прогона и
157 машин, обработан только новый файл. 0 строк ERROR. Тестов: 61.

**Мелочь по итогам:** строка лога «no feeds in ...» вводила в заблуждение (файлы
есть, новых нет) и печаталась каждый тик — переведена в DEBUG с корректным
текстом, на это добавлен тест о «тихом» простое.
